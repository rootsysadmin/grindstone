## Modules System Revamp — set-bonus tracking dropped, per-character "Set" replaces it

The earlier "Console gear system — Cartridge vs. Module" entry below described `setPieceCount`/`setBonusText` (same-shape stacking set bonus) as a real mechanic worth tracking. Revisited directly with the user: **that stacking-bonus tracking isn't needed at all** — those 3 columns (`setName`/`setPieceCount`/`setBonusText`) were dropped from the shared `modules` table entirely (cross-cutting `apps/*` change, see root `docs/progress.md`), which also wiped the 2 seeded Cartridge rows' fabricated set-bonus text (already flagged as unsourced/approximated when seeded — no real data lost).

**Replaced by a per-character "Set"**: 1 Cartridge target + up to `maxAugmentSlots` (6-8) Module targets, built from `moduleTargets` rows already scoped to a character via `forCharacterId` — no new field/table, scoping a target to a character *is* putting it in their Set (the user's own call, simpler than an `inSet` flag or join table). No hard uniqueness/count enforcement (also the user's call) — purely informational counts, same soft-guidance style as the existing slot-count stepper. New `apps/web/src/features/roster/ModuleSetSection.tsx` shows/builds a character's Set directly from the roster page; `AugmentSlotsSection.tsx`'s equip picker now filters to just that Set (with a manual "show full catalog anyway" fallback for a character with no Set yet).

**Also closed a real gap, not previously flagged**: Cartridges' main stat is RNG-rolled per pull (per the "Console gear system" entry below), and the schema already had the right shape for tracking that distinctly from substats (`ownedAugments.mainStat`, `moduleTargets.mainStatTarget`) — but no UI anywhere actually let you edit an owned piece's main stat, level, or substats. `AugmentSlotsSection.tsx`'s equipped/in-bag cards are now click-to-expand with editable main stat/level/substat fields, wired to the already-existing (but previously unused) `useUpdateAugment()`/`PATCH /augments/:id`.

Verified via direct API (no Playwright in this environment): confirmed `GET /modules` no longer returns the 3 dropped fields; created a target scoped to Zankou (character id 1) via `POST /modules/:id/targets`, confirmed it appears in the new flat `GET /module-targets`; created an owned augment, equipped it to Zankou, `PATCH`ed its `mainStat`/`level`/`substats` and confirmed all three persisted distinctly; unequipped/deleted the test augment and target row, confirmed `module-targets`/`augments` back to original baseline. `pnpm typecheck`/`pnpm build` clean throughout.

## Stage 10 — no official update feed exists

Checked directly before building anything: NTE has no official RSS/JSON feed or public API for patch notes, banners, events, or redeem codes. Official channels are the in-game announcement board, Twitter/X (@NTE_EN), and Discord's #announcements — none structured or fetchable. Also checked whether any fan site's own API/feed could stand in — none held up: the official site (`nte.perfectworld.com`) is a JS-rendered SPA with no discoverable static feed, and every candidate guide/wiki site tested (Game8, NTEGuide, NTEbuild, GameWith, TheGamesWiki, the Fandom wiki including its `api.php`, nte-wiki.com) either returned 402/connection-reset to a direct fetch or simply doesn't publish one. This is why Stage 10 (root `docs/progress.md`) ended up building a community data repo instead of a connector to an existing source — there wasn't one to connect to.

Sources checked: [Game8 patch notes](https://game8.co/games/Neverness-to-Everness/archives/592075), [NTE official site](https://nte.perfectworld.com/), [GameSpot codes article](https://www.gamespot.com/articles/neverness-to-everness-codes/1100-6539804/), [NTE Guide patch notes](https://nteguide.com/en/guides/patch-notes/).

## Stage 4 — character banner pity correction

**Correction: character banner hard pity is 90, not 80.** All 4 seeded Character-type banners (Alluring Shadows, The Ichi-Daime, Surfing All Channels!, Misty Tipsy Style) had `pity: 80` — corrected by the user directly to **90**. Weapon/Arc banner pity (60) wasn't challenged and stands. The Standard banner's pity cap is still unsourced (seeded with no value, `source: "manual"`).

Considered whether this warranted a real flat-default-plus-override mechanism (mirroring `skills.maxLevel`'s nullable override of the game-wide `gameSettings.maxSkillLevel`), since the same "90" was duplicated across 4 rows. Decided against it, by the user's call: unlike skill max level, pity genuinely varies per banner *type* (Character 90, Arc 60, Standard unknown) — there's no single flat value that would cover it the way one `maxSkillLevel` covers nearly every skill, so a proper version of that pattern would need a new type-keyed default table for a fact currently duplicated across only 4 rows. Not worth it at this scale — fixed the 4 rows directly instead, same as any other master-data number field.

The original `config.ts` (written in Stage 0, before any research) copied terms straight from the design mockup, on the assumption they were placeholder/fictional flavor text. Web research at the start of Stage 1 found the opposite: the mockup uses real NTE character names (Zankou, Iroi, Shinku, Nanally, Hotori, Daffodill, Jiuyuan, Linko... — confirmed via tier-list sites, e.g. Zankou is literally "the Version 1.3 newcomer") and mostly-real terminology. Two things the mockup got wrong, corrected in `config.ts`:

- **Character dupe/rank-up system is "Awakening"**, not "Sigil" — NTE has 6 Awakening Levels, chosen in any order, not a linear S0–S7 bar. ("Sigil" in the real game refers to a specific Mythic Weapon in the "999 Nights" mode — unrelated.) Sources: [NiveauMax Awakening guide](https://www.niveaumax.com/en/jeux/neverness-to-everness/guides/astuces/eveils-personnages-guide), [Kaiden.gg guides](https://www.kaiden.gg/nte/guides/).
- **6 elements ("Espers"), not 5**: Cosmos, Anima, Incantation, Psyche, Lakshana, Chaos. The mockup's roster only showed 5 (no Psyche character in the sample rows). Source: [Kaiden.gg Esper Cycles](https://www.kaiden.gg/nte/guides/esper-cycles-and-reactions/).

Confirmed accurate: Arc weapon types are Solid/Liquid/Gas/Plasma/Synthesis; premium currency is Annulith (aka Crystals, 160 = 1 pull); banner-specific pull tickets are Solid Dice (limited character banner), Fabricated Dice (standard banner), Tri-Key (Arc/weapon banner, 10-pull only). Source: [thegamearchives currency guide](https://thegamearchives.com/2026/04/25/neverness-to-everness-currency-guide-how-premium-currency-and-pulls-work/), [ldshop.gg gacha guide](https://www.ldshop.gg/blog/nte/gacha-system-currency.html).

**Known simplification, not yet corrected:** the real gear system is called **Console**, made of two distinct pieces — **Cartridges** (1 main stat + 4 substats, Relic-equivalent) and **Modules** (2 fixed stats + 4 substats, block-shaped Type II/III/IV, 2pc/4pc set bonuses). The approved build plan (screen 27 / `docs/build-plan.md` Stage 1) only allocated one "Modules" master-data tab, matching the mockup's single-entity treatment. Stage 1's `modules` table and seed data represent NTE Modules specifically, not Cartridges. If Cartridges need their own master-data tab later, that's a schema addition, not a fix — flag it to the user before doing it, since it's scope beyond what was approved. Source: [nevernessnte.org Console guide](https://nevernessnte.org/guides/console-modules-guide/), [prydwen.gg Modules](https://www.prydwen.gg/neverness-to-everness/guides/modules-generic).

**Not verified, used as-is from the mockup:** "Fons" and "Beetle Coins" as secondary currency names — no source found confirming or denying these. They're left out of `config.ts`'s currency list (which now only has research-confirmed entries) rather than risk seeding fabricated data. If real names surface later, add them.

**Approximated, not sourced:** the two seeded Module sets ("Crimson: Twin Butterflies", "Lost Radiance" — set *names* are real, spotted in the mockup's screen 02) have invented `setBonusText` numbers (2pc/4pc effect percentages) — no source was checked for their actual real values. Fix these via the master data editor once the real numbers are known; they're seeded as `source: "manual"` precisely so they read as needing review, not as verified facts.

**Scope decision, later reversed:** `currencies` was not a master-data DB table/tab in Stage 1, even though the approved plan's Data model section listed it — the actual mockup screens (24-30) only covered 8 entity tabs and didn't include a Currencies tab. Currency names/keys stayed in `config.ts` as static per-game config. **Reversed in a later follow-up** (see root `docs/progress.md`'s "Currencies become master data" entry) once the user shared a new mockup screen for it — currencies are now a real master-data entity (`games/neverness-to-everness/seed/currencies.json`), seeded with the four already-sourced above (Annulith, Solid Dice, Fabricated Dice, Tri-Key). The user confirmed at that point: the mockup's "Everness Ticket" example doesn't exist in the real game (these four are correct), and NTE has several more real currencies beyond these four that weren't seeded — not a priority for that pass.

**Resolved conflict:** the mockup lists Zankou's ascension material as "Crimson Filament" (screens 02, 10, 15); [Game8's Zankou page](https://game8.co/games/Neverness-to-Everness/archives/610918) says "Nest Guard Fragment". Asked the user — went with **Nest Guard Fragment** (the independently-verified source) for Zankou's `ascensionMaterialId`. Crimson Filament is still seeded as one of Zankou's skill-upgrade materials, matching the mockup's skills section, since that specific claim wasn't in question. Other characters' materials/dates are taken from the mockup as-is (not individually re-searched) per the trust level established below — only this one was independently re-checked and found to conflict.

**Console gear system — Cartridge vs. Module, per the user's direct knowledge (not independently sourced).** A character equips exactly one Cartridge (from a fixed catalog, no set bonus) plus several Modules (variable count per character, 4–8). Modules are a fixed set of pieces each with a unique shape (slot type 2/3/4); RNG substats are locked in on acquisition and never reroll. Equipping `setPieceCount` Modules of the *same shape* unlocks a set bonus; extra copies beyond that just add raw stats. A given Module shape is normally farmed several times over for different characters, each wanting different substat priorities — this is the normal case, not an edge case, and drove the `module_targets.forCharacterId` design (see root `docs/progress.md`). The two seed rows previously labeled generic "modules" (Crimson: Twin Butterflies, Lost Radiance) were corrected to `pieceType: "Cartridge"` — their fabricated main-stat/set-bonus text was cleared rather than kept, since it no longer fits what's now known about Cartridges specifically.

**Stage 2 — progression caps and module slot counts.** `config.ts`'s `maxCharacterLevel`/`maxAscension`/`maxSkillLevel`/`maxEquipmentLevel` (added for the build-completion ring) come from the mockup (screens 02/08: level 70/**80**, ascension A5/**A6**, skills X/**12**, Arc Lv 80/**80**) — trusted per the mockup's established trust level (only Awakening naming and the element count were ever flagged as wrong; Ascension as a level-cap-raising track distinct from Awakening was never flagged, so it stands). Per-character `maxAugmentSlots` (module slot count, 4–8 per the user) is mockup-sourced for Zankou only (6, screen 02's six visible slots) — the other eight characters' counts (4–8, varied) are approximated for seed-data variety, not individually sourced; flagged as `manual`/`auto`-inherited rather than independently verified, same as other approximated fields in this file.

**Correction: skill max level is 10, not 12.** The mockup's X/12 skill progress display turned out to be inaccurate — corrected by the user directly to **10**, matching Wuthering Waves' (independently, separately sourced) skill cap. **MC** (the player-insert protagonist character) is a known exception at **11** — not seeded yet, but when MC is added, set `maxLevel: 11` on each of their skill rows (the per-skill override field — see root `docs/progress.md`'s "per-skill max level override" entry) rather than changing the game-wide default.

Sources: [Game8 Zankou materials](https://game8.co/games/Neverness-to-Everness/archives/610918), [Prydwen Zankou guide](https://www.prydwen.gg/neverness-to-everness/characters/zankou).
