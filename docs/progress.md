## Per-table export/import gains sub-item data — a new JSON format, not an extension of CSV

The gap: a full-game bundle export (`gameBundle.ts`) has carried the 7 "child row" tables (level-cost bands, module targets, event rewards, material sources) for a while, but the per-table CSV export/import (`masterData.ts`'s `export.csv`/`import.csv`) never did — a flat `SELECT *` on one table, explicitly scoped out of that work at the time (see the "Real-world-use fixes" entry below, point 4). That gap became a real problem as more sub-item data accumulates per character/weapon/skill/module/event — table-level export/import is the only practical way to bulk-edit that data outside the browser UI.

**Design pivot during planning, driven directly by the user's actual goal.** The first plan was to embed sub-item data into the existing CSV as JSON-blob columns (one extra column per child table, e.g. a `levelCosts` column holding a JSON array per row). Asked the user to confirm that format; their answer reframed the real goal: *"i want to be able to create the initial seed data from the exported data in some easier manner"* — i.e. the export's job isn't just round-tripping, it's being a practical starting point for hand-authoring `games/<slug>/seed/*.json`. Since seed data and the full-game bundle are already **byte-identical in shape** (flat arrays, slug-based FK references, no numeric ids — `gameBundle.ts`'s own doc comment says so directly), a CSV-with-embedded-JSON would have been a *worse* match for that goal than just reusing the bundle shape directly, scoped to one entity. Pivoted to a new **per-table JSON export/import** instead, sitting alongside the untouched CSV buttons rather than replacing them (CSV stays useful for quick flat-field spreadsheet edits; JSON is for anything with sub-items or aimed at seed authoring).

**Backend — scoped the existing bundle machinery rather than building a parallel one.** `exportGameBundle(gameId, only?: EntityKey[])` gained an optional scope parameter (`gameBundle.ts`): still queries every entity's rows unconditionally (a scoped entity's own relation fields, e.g. a character's `elementSlug`, may point outside the scope and still need a real slug), but only *attaches* the requested entity's array and its associated child-table arrays to the output bundle. New `childBundleKeysForEntity` map (`characters`→`characterLevelCosts`, `skills`→`skillMaterials`+`skillLevelCosts`, `modules`→`moduleTargets`, `events`→`eventRewards`, `materials`→`materialSources`, `equipmentItems`→`equipmentLevelCosts`) is the one place that entity↔child-table association is declared, reused by both the export scoping and (implicitly) by nothing else yet — `childRows.ts`'s route registration and this map are still two independent lists, not unified, since unifying them wasn't needed for this change.

**A real latent bug found and fixed while scoping the import side, not a hypothetical.** `importGameBundle`'s relation-slug resolution only ever checked an in-memory map built from *this same import payload* — fine for a full-bundle import (every entity is always present) but broken for a genuinely scoped one: importing just `characters.json` would try to resolve `elementSlug`/`ascensionMaterialSlug` against an empty map (since `elements`/`materials` aren't in that payload) and silently null them out, even though those rows already exist in the database. Fixed with a new `resolveSlugId()` helper — check the in-memory map first (unchanged fast path for a full import), fall back to a `gameId`+`slug` DB lookup when absent. Applied everywhere a slug gets resolved: the main entity loop's own relation fields, and all 7 child-table blocks (previously `materialsMap.get(...)`-style direct lookups on maps built only from the current bundle). This is what actually makes "export one entity, hand-edit, re-import" and "hand-author a new seed file referencing existing rows" both work correctly.

**New routes, one per entity** (`GET .../:apiPath/export.json`, `POST .../:apiPath/import.json` in `masterData.ts`'s existing per-entity loop, so every entity gets this for free, matching how `duplicate` was added generically) — same multipart-or-JSON-body handling as the existing whole-game `/export`/`/import` routes, just delegating to the newly-scoped `exportGameBundle`/`importGameBundle` calls.

**Frontend:** `jsonExportUrl()` + `useImportJson()` (`master-data/api.ts`, mirroring `csvExportUrl`/`useImportCsv`) and two new buttons in `DataTable.tsx` — IMPORT JSON / EXPORT JSON next to the renamed EXPORT CSV — both tooltipped with the one-line "includes sub-item data" distinction so the two formats' purposes are visible without reading code.

**Verified directly via the real dev API (no Playwright available in this environment):** confirmed `export.json` for characters/skills/modules/events/materials/equipmentItems all correctly scope to just that entity + its real child arrays, with `moduleTargets`/`eventRewards`/`materialSources` slug references resolving correctly against real seeded data; round-tripped a real event reward's quantity through export→edit→`import.json`→re-export and got a clean update-in-place (`eventRewards: {updated: 5}`), then reverted it back to the original value the same way; created a brand-new `characterLevelCosts` row via a payload containing *only* `characterLevelCosts` (no `characters`/`materials` arrays at all) referencing an existing character and material purely by slug — confirmed it resolved and inserted correctly via the DB-fallback path, then deleted the test row directly. `pnpm typecheck`/`pnpm build` clean across all three workspaces throughout. Dev servers kept running per project convention.

**Found, not fixed — flagging for the user directly, not just here:** the real dev DB's `skill_materials` table has 5 rows with dangling `skill_id` references (1, 2, 3, 5, 6) pointing at skill rows that no longer exist — the current `skills` table's ids start at 8. Exporting skills today correctly surfaces this as `{skillSlug: null, materialSlug: null}` rather than crashing or silently fabricating a value, but the underlying associations are already lost; this predates this stage's changes (confirmed identically reproducible via the unmodified full-game bundle export) and most likely dates to an earlier session's test-data cleanup that deleted skill rows without cascading their `skill_materials` links. Not cleaned up here since it's real (if broken) data, not something this task touched.

## Duplicate-then-rename bug: slug (and its image) never followed a name change

Caught by real use: duplicating a row created it as `"<name> (copy)"` with a slug derived from that at duplicate time — correct in isolation, but the record editor's rename UI only ever changes `name`, and `PATCH` never recomputed `slug` from a plain name edit. Since image lookup (`findImageUrl`/`saveImage` in `apps/api/src/core/images.ts`) matches by `slug`, not `name`, renaming a duplicate back to its real name (`"X (copy)"` → `"X"`) left `slug` permanently stuck at `x-copy` — the row's picture (still sitting on disk as `x.<ext>`) could never resolve again. Two complementary fixes landed, both requested directly rather than picked by me alone:

**1. Duplicate asks for the final name up front.** `POST .../:id/duplicate` now accepts an optional `{ name }` body (`duplicateRow.ts`'s `duplicateMasterDataRow` gained a `name?` param, falling back to the old `"<name> (copy)"` default when omitted — existing callers/scripts still work unchanged). New `DuplicateRowDialog.tsx` (`apps/web/src/features/master-data/`, matching the app's existing self-contained-overlay dialog convention — no shared `Modal` component exists anywhere in `apps/web`) prompts with the name pre-filled as `"<name> (copy)"`, editable before the row is actually created — so the slug is computed correctly from the *real* name at creation time, no rename ever needed. Wired into both `DataTable.tsx`'s row-level "duplicate" action and `CharacterSkillsSection.tsx`'s inline "⧉" skill-duplicate button (the two existing call sites of `useDuplicateRow`).

**2. A plain rename now keeps slug (and the image file) in sync generally**, not just for duplicates. New `renameImage()` in `images.ts` moves the on-disk file to match a new slug (no-op if none is set), and `PATCH /:id` in `masterData.ts` now derives a fresh slug from `body.name` whenever the name actually changed and the caller didn't *deliberately* supply a different slug. The tricky part: no entity exposes a slug input anywhere, so `RecordEditor.tsx`'s save always round-trips the row's existing `slug` unchanged inside `body` (its form state starts as `{...row}`) — a naive `if (body.slug) use it` check (the pre-existing behavior) meant `body.slug` was *always* truthy and always stale, so it would never fall through to recomputing from `name`. Fixed by only treating `body.slug` as an explicit override when it actually differs from the stored value; otherwise a changed `name` drives the recompute. `renameImage` is called after a successful update whenever the resulting slug differs from the row's prior one, gated on `config.hasImage` same as every other image call site.

**Verified directly via the running API (no Playwright available in this environment — browser-level dialog rendering wasn't clicked through, only `tsc --noEmit` clean + Vite transforming the new/changed files with no errors):** PATCHed a real character (Nanally, id 9) sending its full round-tripped form body with only `name` changed to "Nanally Test" — `slug` came back as `nanally-test` and the on-disk `nanally.avif` was renamed to `nanally-test.avif`; a follow-up GET resolved `imageUrl` correctly under the new filename; renaming back to "Nanally" round-tripped both the slug and the file back to their original names exactly. Duplicated Zankou via the new endpoint with an explicit `{name: "Zankou Alt"}` — got `slug: "zankou-alt"` immediately, no rename ever needed; a bodyless duplicate call still fell back to the old `"Zankou (copy)"` / `zankou-copy` behavior, confirming back-compat. All test rows deleted afterward; character list confirmed back to its original 9 rows with images intact. `pnpm typecheck` clean.

## Configurable rank/rarity tiers with color coding

Rank/rarity was handled three inconsistent ways: characters/equipment used a per-game hardcoded string list (`games/<slug>/config.ts`'s `ranks: ["S","A","B"]` for NTE, `["5★","4★"]` for Wuthering Waves) with no color; materials used a separate, unrelated `tier: 1-6` integer with its own hardcoded 6-color ramp baked into `MaterialSwatch.tsx`; currencies had no rank concept at all despite genuinely having one in both real games. The user wanted one visual rank system, but explicitly **not** a fixed universal table — different games use different tier counts (NTE: 3, Wuthering Waves: 2, others seen with 5+ in Genshin/HSR), so tier names, count, and colors needed to be freely configurable per game.

**Same move already made once for currencies** (`docs/progress.md`'s "Stage 1 follow-up — Currencies become master data"), reapplied to `ranks`: a new per-game, fully editable **`rankTiers`** master-data table (`{name, level, color}`) replaces the hardcoded config list entirely. Applies to **characters, equipment, and materials** (materials' existing 6-tier system unified onto this same mechanism) **and currencies** (new — left unset until assigned by hand). **Not** modules/echoes — the user confirmed cartridges/modules don't level at all and anything below top-tier isn't worth tracking there, so no schema addition for them. `pull_log.rank` (a denormalized text snapshot of an item's rank *at the time it was pulled*) is untouched on purpose — a frozen historical record shouldn't retroactively change if a tier definition is edited later.

**Schema:** new `rank_tiers` table (`level` integer — ascending = stronger, drives sort order, not just display; `color` hex text). `characters.rank`/`equipmentItems.rank` (text) and `materials.tier` (integer) replaced by `rankTierId` (relation to `rankTiers`); `currencies` gained a new, optional `rankTierId`. **Real data was at stake this time** (unlike earlier stages where a from-scratch reseed was safe) — done as a proper two-phase migration: Migration A added `rank_tiers` + nullable `rank_tier_id` columns alongside the old ones; a one-off backfill script (`apps/api/src/db/backfillRankTiers.ts`, run once via `tsx`, then deleted once done — not a permanent part of the app) seeded `rankTiers` rows per game (character/equipment ranks from each game's now-deleted config order, colors defaulting to the blue/purple/orange top of the ramp; materials' 6 tiers reusing the *exact* old `MaterialSwatch` hex values, preserving current appearance exactly) and backfilled every existing row's `rankTierId` by matching its old value; Migration B then dropped the old `rank`/`tier` columns. Verified 100% backfill match on every character/equipment row across both games before dropping anything.

**A design correction found while implementing, not in the original plan:** the approved plan called for a provenance-safe merge on the full-game bundle import for this data — but `gameBundle.ts`'s `importGameBundle` already does a blind natural-key upsert for *every* table it touches, including the main 8 entities, which also carry a `source` column. That's intentional existing behavior (a bundle export/import is a full-fidelity backup/restore tool, a different job from `updateSync.ts`'s provenance-safe sync) — no code change was needed for `rankTiers` here at all, since it's just entity #9 through the same already-generic `entityDependencyOrder`-driven loop. Confirmed via direct export: `rankTiers` and every `rankTierId` reference round-trip correctly with zero `gameBundle.ts` changes.

**Frontend:** new `apps/web/src/components/rankVisuals.tsx` — `hexToRgb`, `RankBadge` (small colored pill, replaces the old position-in-array `RankBadge.tsx`/`rankRgb` this session had built earlier for pull-log display), and `RarityFrame` (colored border + soft diagonal gradient behind an image, generalizing `MaterialSwatch`'s existing diagonal-stripe technique — not a solid color block, matching common gacha UI conventions). `MaterialSwatch.tsx` now takes a resolved `color` directly instead of a hardcoded tier-keyed palette. New `useRankTiers()`/`useRankTierMap()` hooks (`master-data/api.ts`) are the one place every screen resolves a `rankTierId` or looks up the game's tiers, instead of re-fetching per screen. Applied to: Roster grid cards (`RarityFrame` around the portrait), the master-data `DataTable`'s image thumbnail column and relation-column rendering (badge instead of plain text for `rankTiers` relations), the record editor's rank picker (colored bullet per option) and new `type: "color"` field (a native color input, used by the Tiers tab itself). `DataTable`'s column sort (from the earlier sorting fix) now special-cases `rankTiers` relations to sort by numeric `level`, not resolved label text — alphabetical only coincidentally worked for Latin letter grades and was never going to generalize.

**Ripple effects from removing `gameConfig.ranks`, found by grep, not by guessing:** `PullLogTab.tsx`/`OverviewTab.tsx` (pull-log rank badges — these match `pull_log.rank`'s frozen text against the game's *current* tiers by name, since that table has no `rankTierId` and shouldn't get one), `LogPullDialog.tsx` (manual pull-entry rank picker + auto-fill from a picked character/equipment row), `spend/spendData.ts` + `spend/api.ts` (the $/top-rank stat — `GameSpendData` gained a `topRankName` fetched alongside everything else per game), `wishlist/TargetsTab.tsx` (same $/top-rank stat) all updated to resolve against `rankTiers` instead of the deleted config array. One genuine ordering flip to get right: the old `ranks` arrays were authored highest-first (`["S","A","B"]`), while the new `rankTiers.level` is ascending (1 = weakest) — every "top rank" lookup flipped from `[0]` to `[length-1]` accordingly.

**A real bug caught by testing, not by inspection:** the Roster page's rank filter, freshly wired to `useRankTiers()`, showed *every* tier in the game — including materials' "Tier 1"–"Tier 6" mixed in alongside characters' actual "S"/"A" ranks — because `rankTiers` is now one shared per-game table across every entity type, not scoped by which entity uses which tier. Fixed by deriving the filter list from the tier ids actually present on a roster character, not the full table. **Known follow-up, not fixed:** the same "shared table, no scoping" issue exists in the record editor's rank picker for every entity — a character's Rank dropdown technically lists materials' Tier 1-6 options too (harmless — you just skip past them — but not clean). Would need a `rankTiers.appliesTo` field or similar to scope properly; left as-is since it's cosmetic, not incorrect, and adding that field wasn't part of the approved plan.

`packages/shared/src/sync.ts`'s `NewMaterialDraft.tier` (a plain 1-6 number, from the Stage 10 sync system) was dropped rather than migrated — a fixed number never cleanly mapped to a per-game custom tier table, and matches how `NewCharacterDraft`/`NewEquipmentDraft` already stay deliberately minimal; a synced material's rank is fillable by hand afterward like any other field a sync doesn't populate. Updated `docs/community-data-repo-starter/schema.md` to match.

**Verified end-to-end (real dev servers, Playwright + direct API, no console errors):** confirmed 100% backfill accuracy for every character/equipment/material row on both games before dropping the old columns; added a new custom tier via the Tiers tab and confirmed the badge/roster-card gradient reflected it immediately; confirmed the Rank column sorts by actual power level, not alphabetically; assigned a currency a rank for the first time and confirmed the badge appeared, confirmed an unset one renders cleanly; confirmed the full-game export includes `rankTiers` with correct slug references. All test data reset afterward. `pnpm typecheck`/`pnpm build` clean throughout. Also found and restarted the dev servers, which had stopped running from an earlier session gap.

## Duplicate a master-data row (generic, with level-cost rows riding along)

Prompted by the level-cost editor fix above: within one character, most skills need near-identical upgrade-material schedules, and there was no way to reuse one you'd already built. What started as "add a copy button to skills" widened over two rounds of clarification into checking the same repetition claim for characters/equipment (the ascension-tree *shape* repeats, though the specific materials differ per character — copy the schedule, then just swap which material each band points to) and Cartridges/Modules (no leveling exists or is wanted for these — confirmed directly with the user, reversing my own initial assumption — but their own fields like `mainStat`/`setBonusText` repeat just as often).

Landed on one generic **"Duplicate"** action instead of three separate "copy from" pickers: clone the whole row (every column), give it a fresh `"<name> (copy)"` / unique slug, and if that entity happens to have a level-cost child table (characters/equipment/skills), clone those rows onto the new id too — modules simply have no such table, so duplicating one just clones its own fields, no special-casing needed to make that true.

**Backend:**
- Relocated `withUniqueSlug` from `apps/api/src/routes/masterData.ts` into `apps/api/src/core/slugify.ts` (pure move, no behavior change) — `core/` isn't supposed to import from `routes/`, and the new duplicate logic needed this helper too.
- New `apps/api/src/core/duplicateRow.ts` — `duplicateMasterDataRow(gameId, key, id)`: loads the source row, inserts a full copy (every column except id/gameId/slug/audit fields) with `source: "manual"`, then — only for `characters`/`equipmentItems`/`skills`, via a small local lookup table — copies every matching level-cost row (`fromLevel`/`toLevel`/`materialId`/`quantity`) onto the new parent id. Fully generic: a module's `mainStat`/`pieceType`/`setBonusText` or a character's `rank`/`elementId` just come along as part of the same full-row copy — no per-entity field list anywhere.
- One route, `POST /api/games/:game/<apiPath>/:id/duplicate`, added unconditionally inside `masterData.ts`'s existing per-entity loop — applies to every entity for free (Characters, Arcs/weapons, Modules, Skills, Banners, Events, Materials...), not gated to the few entities that were actually asked about, since the marginal cost of making it generic was near zero.

**Frontend:** `useDuplicateRow(config)` in `api.ts` (same shape as `useDeleteRow`, generic over `config`). A "duplicate" text action next to "delete" on every entity's row in the shared `DataTable.tsx` — free on every tab. Additionally, a "⧉" duplicate button on each inline skill row in `CharacterSkillsSection.tsx` (next to its "✕"), since that's the original, most direct use case — cloning a sibling skill's schedule while looking at one character's skill list — worth having there too, not only on the flat Skills tab.

**Verified end-to-end (real dev servers — found stopped from a prior session gap, restarted per the "keep the app running" convention — Playwright + direct API, no console errors):** built a skill with 3 level-cost rows across 2 bands (one band with 2 materials), duplicated it — new skill got the exact same 3 rows with new ids, `source: "manual"`; edited the copy's quantity and confirmed the original's row was untouched (independent, not shared); duplicated a character and confirmed every field copied correctly with a unique slug/name, and confirmed its skills were *not* cloned (skills aren't a level-cost child of a character, by design — only within-skill schedules ride along, never cross-entity children); duplicated a Cartridge module and confirmed every field (`pieceType`, `maxLevel`, `setName`, etc.) copied with no level-cost rows created (none exist for modules); duplicated the same skill twice and confirmed clean slug de-duplication (`-copy`, then `-copy-2`); confirmed both the generic `DataTable` "duplicate" button and the inline skill "⧉" button work correctly in a real browser. All test rows deleted afterward — the seeded state was verified back to its original shape before finishing. `pnpm typecheck`/`pnpm build` clean throughout.

## Real-world-use fixes: table sorting, element field cleanup, level-cost editor UX, export completeness

Four issues surfaced by actually using the app against real NTE data (prompted by a screenshot of a real skill's per-level upgrade table — "To Level 2" through "To Level 10", each level needing several distinct materials at once):

1. **Master-data tables couldn't be sorted.** Added client-side sort to `DataTable.tsx` — click any column header to cycle asc → desc → off (back to server/insertion order), with a `▲`/`▼` indicator. One shared comparator (`compareValues`) handles relation columns (sorts by resolved label, not raw id), numbers, booleans, and nulls-last — applies uniformly to every entity tab, nothing per-entity to configure.
2. **`elements.strongVsElementId`/`ascensionMaterialId` removed** — confirmed via direct query that both were `null` on every row in both seeded games before dropping (clean migration, `0007_condemned_nemesis.sql`, plain `DROP COLUMN` — no rebuild-table workaround needed). Not to be confused with `characters.ascensionMaterialId`, a distinct, unrelated field left untouched. This also retired a documented "known limitation" in `gameBundle.ts` about self-referencing slugs (the elements table was the only place that pattern existed) — comment reworded since no relation is self-referencing anymore.
3. **Level-cost editor (`LevelCostsSection.tsx`) rework.** Two real problems, both visible in the screenshot's shape: it force-sorted every render (`[...rows].sort(...)`), so a newly-added band could jump elsewhere in the list instead of staying put; and it only supported one band = one material at a time, when a real level needs several materials at once (the screenshot's "To Level 2" alone needs 3). Fixed by (a) deleting the force-sort — rows now render in the order the API returns them (SQLite's default is insertion order), which alone guarantees a new band lands at the bottom; (b) a new `groupIntoBands` — a *stable, first-seen* grouping by `(fromLevel, toLevel)`, not a sort, so several existing rows sharing a level cluster into one visual band without changing where that band sits in the list. Each band now shows one editable From/To pair (editing either updates every row in that band together — a band is conceptually one level range, so letting one material line's level drift from its siblings would desync a group meant to move as one) plus a per-band "+ add material" that appends another row sharing that band's current From/To. "+ ADD LEVEL" replaces "+ ADD BAND", defaulting to continue on from the last band (`lastBand.toLevel → lastBand.toLevel + 1`). Pure frontend rework — the underlying flat `{fromLevel, toLevel, materialId, quantity}` row shape already supported "one level, several materials" (several rows sharing a band), so no schema or API change was needed.
4. **Full-game export/import never included the three level-cost tables** — confirmed by direct grep, a plain oversight: `materialSources`/`skillMaterials`/`moduleTargets`/`eventRewards` already get bundle export/import treatment, but `characterLevelCosts`/`equipmentLevelCosts`/`skillLevelCosts` were simply missing, meaning this data had zero backup/restore path. Extended `gameBundle.ts` the same way those four already work: exported with parent/material references as slugs, imported matched on natural key (`parentSlug + fromLevel + toLevel + materialSlug`) so re-importing updates in place. Scope decision made with the user: fixed via the full-game bundle only, not by also extending each entity's own per-table CSV export — CSV is a flat single-table dump everywhere in the app (materials' CSV doesn't carry material sources either), so making it a special case just for level costs would be new, inconsistent behavior; the full-game bundle is already the established mechanism for child-row portability.

**A design correction made mid-implementation, worth recording:** the approved plan for #4 called for a provenance-safe merge (skip a `manual`/`override` row, like `updateSync.ts` does) — but implementing it surfaced that `gameBundle.ts`'s `importGameBundle` is *already* a blind natural-key upsert for every table it touches, including the main 8 entities, which also carry a `source` column. That's intentional, existing behavior: a bundle export/import is a full-fidelity backup/restore/move-between-installs tool, not a partial external-data merge — a different job from `updateSync.ts`'s sync, which deliberately never touches a manual/override row. Matching the plan's provenance-guard as written would have made the 3 new tables behave inconsistently with every other table in the same function. Implemented the blind upsert instead (consistent with the other 12 tables this function already handles), documented the distinction directly in `gameBundle.ts`'s doc comment so the two functions' upsert styles aren't cross-contaminated later.

**Verified end-to-end (real dev servers, Playwright + direct API, no console errors):** sorting a column toggles asc/desc/off correctly, confirmed against Materials; Elements record editor no longer shows the two removed fields, existing rows still load/save correctly; created a band with 2 materials + a second band via "+ ADD LEVEL"/"+ add material", confirmed via raw page inspection that both bands render correctly grouped with the right From/To and material counts, confirmed the 2nd band defaulted to continuing from the 1st's `toLevel`; edited a band's From via the UI and confirmed (via network capture + direct API read) both rows in that band updated together while the sibling band was untouched; exported the full bundle and confirmed `characterLevelCosts` appears with correct slug references; re-imported a modified copy and confirmed update-in-place (no duplicate rows, `created: 0, updated: 2`). All test rows deleted afterward. `pnpm typecheck`/`pnpm build` clean throughout.

## Stage 10 follow-up — level-up material costs via the sync system (Option A: provenance)

Prompted by the add-character/add-weapon dialogs' own note that material requirements sometimes can't be filled in at add time: that's fine for hand-entry (correct it later via the level-costs child-row editor), but it exposed a real gap in the repo-sync system — `characterLevelCosts`/`equipmentLevelCosts`/`skillLevelCosts` had **no provenance column at all**, unlike every other synced entity (characters, banners, events, codes, materials themselves all have `source: auto|manual|override`). Without it, there was no way to sync cost bands without either blind-overwriting a hand-corrected number or not being able to sync them.

Two options were on the table: add provenance to the level-cost tables and treat cost bands as a first-class synced thing (**Option A**, consistent with every other entity), or an additive-only workaround with no schema change (Option B). Chose **Option A**.

**Schema:** `source` (`auto`/`manual`/`override`, default `manual`) added to all three level-cost tables — pure additive migration (`0006_zippy_shinko_yamashiro.sql`). The existing generic `registerChildRoutes` PATCH-by-id route (already registered for all three tables) needed no changes — it's what verification used to hand-flip a row to `manual`, at its parent-scoped path (`characters/:parentId/level-costs/:id` etc.) — note the `flatPath` variant is GET-only, PATCH/DELETE always go through the parent-scoped path.

**New `LevelCostUpdatePayload`** (`packages/shared/src/sync.ts`) — a fourth top-level `UpdateKind`, not nested inside a banner: cost data realistically surfaces well after a character's debut, as its own separate discovery event, unlike a new character/weapon (which does belong nested in its banner, see the follow-up below). `targetKind` (`character`/`equipment`/`skill`) + `targetSlug` identify an **already-existing** parent — this update attaches data, it never creates the target itself (that stays the banner's `newCharacter`/`newEquipment` job). `newMaterials?: NewMaterialDraft[]` lets a payload introduce materials that don't exist yet (same minimal-honest-field-set convention as `NewCharacterDraft`: `name`/`tier`/`category` only). `bands: LevelCostBandDraft[]` are `{fromLevel, toLevel, materialSlug, quantity}`.

**Per-band provenance, not full-replace.** Unlike `codeRewards`/`eventRewards` (delete-then-insert whenever their parent update applies — fine, since those rows aren't independently user-editable), each level-cost band is matched to an existing row by natural key (`targetId + fromLevel + toLevel + materialId`) and upserted individually: no existing row → `auto`; existing `auto` row → updated in place; existing `manual`/`override` row → left completely untouched while sibling `auto` rows in the same update still apply. This matters because bands *are* independently hand-correctable via the level-costs child-row editor, unlike a reward line. New `upsertMaterialDraft` in `apps/api/src/core/updateSync.ts` mirrors `upsertCharacterDraft`/`upsertEquipmentDraft`; the per-band apply logic is three explicit code paths (character/equipment/skill) rather than one dynamic-column generic, same reasoning as keeping the character/equipment draft upserts separate — Drizzle's typed columns differ enough (different parent-id column name per table) that a generic needs casting throughout.

**A new correlation pattern this introduced:** a band referencing a brand-new material must compute the *same slug* the backend will assign it (`slugify(name)`), since `newMaterials` are upserted independently of the bands that reference them, then resolved by slug afterward — unlike the banner's `newCharacter`, whose returned id is used directly server-side, with no client-side slug-matching involved. The frontend's `slugify` (`apps/web/src/features/sync/slugify.ts`, extracted out of `LogUpdateDialog.tsx` where it used to live inline) is a byte-for-byte mirror of the backend's `apps/api/src/core/slugify.ts` for exactly this reason.

**Frontend:** Log Update dialog gained a fourth type ("Mat. costs") — a target-kind picker + search-and-pick (reusing the same `useEntityList` pattern the banner form already uses), and a new `LevelCostsEditor.tsx` (bands editor, same add/remove-row idiom as `RewardsEditor`/`GrantsEditor`) where each row carries its own EXISTING/NEW material toggle, since one update can mix materials that already exist here with ones that don't.

**Community data repo:** new `level-costs/` subfolder + `docs/community-data-repo-starter/schema.md` section + `scripts/validate.mjs` support (kind/target/band-shape checks, tested directly against a valid and an intentionally-broken sample file — every real issue flagged, valid file passed clean).

**Verified end-to-end (real dev servers, Playwright + direct API, no console errors):** applied a payload naming a new material and two bands (one existing material, one new) for an existing character — material created `auto`, both bands created `auto` with correct values; re-applied with changed quantities — bands updated in place, no duplication; hand-flipped one band to `manual` via the child-row PATCH route and re-applied with yet another quantity change — that row stayed untouched while its `auto` sibling still updated; applied a payload with an unresolvable `targetSlug` — whole payload correctly skipped, nothing created; drove the Log Update dialog's new form directly in a real browser — APPLY TO MY DATA created the expected row (confirmed via API), CONTRIBUTE TO REPO produced a correctly-shaped `games/<slug>/level-costs/<date>-<target-kind>-<target-slug>.json` deep-link with the new material's slug correctly matching its `newMaterials` entry. All test rows/materials deleted and sync-settings reset afterward. `pnpm typecheck`/`pnpm build` clean throughout.

## Stage 10 follow-up — banners can introduce a new character/weapon

You caught another real gap right after the reward-crediting follow-up: `BannerUpdatePayload.featuredCharacterSlug` only ever *linked to* a character that already existed locally — if a banner introduced a brand-new character (the normal case; new characters debut via banners, not a separate announcement), the slug simply failed to resolve, `featuredCharacterId` stayed null, and the character itself was never created. Someone relying purely on repo sync, never touching the master-data editor by hand, would get a banner with no featured character and no way to ever build it — exactly the "sync-only" user the whole feature exists for.

**Scoped to banners only** (new characters/weapons debut via banners in practice, not events) and **nested inside the banner payload** rather than a separate top-level "character" update kind — a debut is one discrete update event, and splitting it into two files a contributor has to remember to add together (and that could land in different PRs, merged out of order) would be worse than the problem it solves.

**Same provenance-safe create/update/skip logic already built for banners/events/codes, extended to the nested character/weapon**: no existing row with that slug → created as `auto`; existing row is `auto` → updated in place (a later, more accurate sync corrects an earlier stub); existing row is `manual`/`override` → left completely untouched, but the banner still links to it (a manually-perfected character shouldn't get orphaned just because a sync ran). New `upsertCharacterDraft`/`upsertEquipmentDraft` in `apps/api/src/core/updateSync.ts`, kept as two small explicit functions rather than one generic one over both tables — Drizzle's per-table column types differ enough that a shared generic would need casting throughout.

**Deliberately minimal field set**: name, rank, element, role, weapon-type, release date for a character; name, rank, type, main stat for a weapon — things an actual banner announcement states. Left out on purpose: `ascensionMaterialId` and `maxAugmentSlots`, neither of which is realistically known at announcement time (they surface later, via datamines/kit guides) — both stay fillable by hand later, same as any other master-data field, and the dialog says so directly.

**Frontend**: the banner form's featured-entity field gained an EXISTING/NEW mode toggle — EXISTING is the original search-and-pick, unchanged; NEW reveals a compact character-or-weapon sub-form (reusing the newly-fetched `entityConfigs.elements` list for the element picker, same one-line addition pattern as the existing currency/material fetches).

**Verified end-to-end via direct API (real dev servers, no console errors):** applied a banner naming a brand-new character by `newCharacter` — a real `auto` character row was created with the given rank/element/role/release-date, correctly resolving the `elementSlug` to its actual id, and the banner's `featuredCharacterId` pointed at it; re-applied the same banner with a changed role and confirmed the character updated in place (same id, no duplicate); manually flipped that character to `source: "manual"` and re-applied the banner with yet another role — confirmed the character was left completely untouched (role unchanged) while the banner still correctly linked to it; confirmed a banner using `featuredCharacterSlug` alone (no `newCharacter`) still resolves against an existing character exactly as before, unaffected. All test rows deleted afterward. `pnpm typecheck`/`pnpm build` clean throughout.

## Stage 10 — Community-sourced update sync (done)

**The original build-plan sketch assumed a real feed might exist; research found it doesn't, for either seeded game.** Checked directly for Neverness to Everness (no official API — Discord/Twitter/in-game only) and, more surprisingly, for Wuthering Waves too despite its much bigger fanbase: the two community projects that specifically tried to expose a public codes API are both dead (`wuwa-api.vercel.app/api/codes` returns `{"codes": []}`; `wuwa.projektcode.com` doesn't resolve), and the actively-maintained tracker (`wuwatracker`, 289 stars, 1,500+ commits) doesn't publicly expose its underlying data. The pattern held across both games: real fan tooling exists, but as silos — everyone curates their own data for their own site, nobody publishes a shared reusable feed. That finding reframed the stage: instead of a connector *to* a feed, this builds the feed — a community-editable, PR-reviewed data repo any Grindstone install can pull from — plus the app-side tooling to consume and contribute to it.

**Scope boundary, agreed explicitly with the user:** this stage built the *app-side* mechanics and drafted the data repo's starter content (`docs/community-data-repo-starter/` — README, schema doc, a dependency-free CI validator script, a GitHub Actions workflow, all tested directly against sample valid/invalid files). Actually creating and hosting that public repo is the user's action, not something done as part of building this codebase.

**Data model:** `redeem_codes` (Stage 5, previously plain user-state) gained a `source` column (`auto`/`manual`/`override`, defaulting to `manual` so every existing/hand-added code stays protected automatically) — the one schema change to an existing table. New: `ingested_update_files` (tracks which community-repo file paths a game has already pulled, so a sync never re-fetches or re-applies the same update twice — the client-side half of "grab only what's new"), `sync_runs` (accountability log, same shape as `savings_rule_overrides`/`spend_budget_overrides`), `sync_settings` (one row, app-wide — the data repo owner/name covers every game, each in its own `games/<slug>/` folder in that repo, mirroring how this app's own `games/<slug>/` folders already work).

**The provenance-safe upsert (`apps/api/src/core/updateSync.ts`) is genuinely new, not a reuse of `gameBundle.ts`'s import path.** Confirmed by reading it: `importGameBundle`'s upsert-by-slug loop blind-overwrites whatever's already there, with no check on the existing row's `source` — reasonable for its own use case (a deliberate, manual "you asked for this" import) but wrong for an automated sync. `applyUpdatePayload` adds the real guard: no existing row → insert as `auto`; existing row is already `auto` → update in place; existing row is `manual`/`override` → skip, completely untouched. This is the one piece of logic the whole stage exists to build correctly, and it's shared by both the community-repo sync and the manually-logged-update path — same function, two callers.

**Listing "what's new" is one GitHub API call regardless of folder depth.** Deliberately the Git Trees API (`git/trees/main?recursive=1`, returns every path in the repo in one response) instead of the per-directory Contents API (which would need one call per subfolder). This resolved a real design question raised mid-planning: whether the data repo should use per-type subfolders (`codes/`, `banners/`, `events/`) or a flat structure with filename prefixes to minimize API calls — with the Trees API, the call count is identical either way, so the choice was made on its own merits instead (subfolders won: matches this app's own `games/<slug>/seed/<entity>.json` convention, browses better on GitHub, and lets CI validation rules target types independently later).

**No cron — "nightly-ish" via check-on-load instead**, matching how every other "keep this fresh" mechanism in this app already works (income projections, task periods, budget status — all computed or triggered on read, never backgrounded). `Shell.tsx` — the one place every page routes through — checks once per mount whether the last sync was over 24h ago and fires `runCommunitySync` if so; no timer process, no scheduler.

**AI-assisted extraction (paste raw patch-notes text, have a model structure it) was designed in detail during planning and then explicitly cut by the user** — "remove the AI bit for now. manual entry only. will come back to AI thing later if I ever need it." This stage ships manual structured entry only (`LogUpdateDialog.tsx`): a type picker (code/banner/event) and the relevant fields by hand, with two independent actions — **APPLY TO MY DATA** (the provenance-safe engine, applied locally) and **CONTRIBUTE TO REPO** (formats the same data into the community repo's file-naming convention and opens GitHub's own pre-filled "create new file" page in a new tab — deliberately not a token-based auto-PR flow, a design choice made explicitly during planning to avoid Grindstone ever needing to store or use a GitHub credential; finishing the PR is one click on GitHub's own UI). If AI-assisted extraction is revisited later, it slots in as an additional way to *fill* this same form, not a redesign of anything here.

**Banner updates support a real featured-character/weapon picker** (reusing the search-and-pick pattern from `wishlist/AddTargetDialog.tsx`), matched to real master-data rows rather than free text — the community-repo schema itself deliberately leaves featured-entity out of the CI-checkable shape (it would need matching against a specific game's roster, which the shared repo doesn't have visibility into), documented as a known gap in `schema.md`, fillable locally after a sync or by hand.

**Two real bugs caught during verification, not by inspection:** (1) the sync-settings inputs on the Data page both defaulted to `key=""` when empty, since the remount-key convention used elsewhere in this app keys on the field's own value — two empty fields in the same parent collided. Fixed by prefixing each key with its field name. (2) `runCommunitySync` let a network/repo-not-found error propagate into an unhandled 500 — caught by testing against a data repo that doesn't exist yet (the real state every install will start in, including this one, until the user creates it). Fixed to fail gracefully (a zeroed summary, no crash, no log entry) — a sync being unable to reach its source is an expected, recoverable condition here, not a server error.

**Verified end-to-end (Playwright + direct API, real dev servers, no console errors after fixes):** hand-adding a code confirmed `source: "manual"`; logging and applying a code, banner, and event through the dialog all landed as `source: "auto"` with the correct derived slug on banners/events; re-applying the same code updated it in place (no duplicate row); flipping that row to `override` via direct API and re-applying confirmed it was skipped, byte-for-byte untouched — the actual "manual/override rows survive" guarantee the original build-plan asked for; the AUTO badge rendered correctly on a genuinely-auto row and correctly did not render on the override row; CONTRIBUTE opened a correctly-formed GitHub new-file URL with the right path/filename/JSON content; community sync against a nonexistent repo returned a clean zeroed summary instead of crashing; Wuthering Waves exercised identically with no special-casing. All test rows deleted and settings reset afterward, confirmed empty via GET.

## Stage 9 — Real-money spend tracker (done)

**Shipped:** screens 32–36 (Overview / Transactions / Subscriptions / Budget / Value) — real mockups you designed and shared as a claude.ai artifact, replacing `docs/build-plan.md`'s original thin sketch. This stage's new code just hadn't picked up that established lesson. **Follow-up fix — "pity at" was ambiguous with the hard-pity cap.** You asked whether "Pity At" meant the banner's fixed cap (80 for N2E characters, 60 for weapons) — it doesn't, it's the per-pull count of pulls since your last top-rank pull, which can be well below the cap for an early natural win, but the label didn't make that distinction and read like it should always equal the cap. **Follow-up fix — RATES panel replaced with a luck-efficiency stat, no more A-rate.** You asked to drop A-rate (occurrence rate on a handful of logged pulls isn't a meaningful stat) and rework S-rate into something based on actual pity spend vs. the theoretical maximum — with the specific rule that where a banner tracks 50/50, losing it still costs real pulls toward the *target*, so the effective denominator should double (e.g. out of 160 instead of 80), since a lose-then-guaranteed-win pair is really one target acquisition that cost up to two full pities. Verified against hand-computed expected values on both seeded games: N2E (two clean wins, 90 cap, no 50/50) → exactly 55.6% (100/180); Wuthering Waves (one lose-then-guaranteed-win pair, 80 cap, 50/50 tracked) → exactly 56.3% (90/160), with the panel correctly appending "· doubled on 50/50 losses" only when the pool tracks it. The panel now shows one hero "PITY USED" stat (with an "X of Y possible" sub-line for transparency) plus Luckiest/Worst below, instead of the old 2x2 S-rate/A-rate/Luckiest/Worst grid.

**Follow-up — edit/delete pulls, dupe-averaged Luckiest/Worst, and Pity Used flipped into a Luck Rate.** Three related asks:

- **Modify/delete a logged pull.** `LogPullDialog.tsx` now doubles as the edit form when opened with an `entry` prop (pre-fills every field from it, title becomes "Edit pull", submit becomes "SAVE", and a DELETE button appears) instead of building a separate editor — reuses `useUpdatePullLogEntry`/`useDeletePullLogEntry`, which already existed in `api.ts` but had no UI calling them. The pity-suggestion autofill (see the "pity at" follow-up above) is skipped entirely in edit mode — it shouldn't silently replace a pull's real historical value with a freshly recomputed "current" one. Each log row in `PullLogTab.tsx` got a ✎ edit / ✕ delete pair, no confirmation dialog, matching the plain instant-delete convention already used by Farm Route and Income Sources rows.
- **Dupes no longer skew Luckiest/Worst.** Pulling the same character multiple times (awakening fodder) used to let each copy count as its own "luckiest"/"worst" data point. `computeRates` now groups history entries by item identity first, averages a character's own pulls, and only then compares averages across characters — the UI shows "(avg of N)" next to the name when N > 1.
- **"Pity Used" renamed to "Luck Rate" and inverted**, per your spec: 100% = won on pull 1, 0% = hit hard pity, linear in between. Per-pull that's `(cap - pityAtPull) / (cap - 1)`; aggregated across entries as `sum(cap - pityAtPull) / sum(cap - 1)` rather than averaging per-entry ratios, so it reduces to the exact per-pull formula for a single entry and still needs no special-casing for 50/50 — a "lost" entry is a real pull that wasn't a lucky win, so it drags the average down same as any other entry. Verified against hand-computed values: a pull-1 win → exactly 100.0%; a win at exact hard pity (90) → exactly 0.0%; a win at pity 45 of a 90 cap → exactly 50.6% (45/89). The stat now color-codes green/amber/pink at 66%/33% thresholds, matching the coverage-bar convention already used elsewhere (Materials tab).

**Verified:** logged pulls across two different Character-pool banner phases and confirmed pity carries across the phase boundary instead of resetting (39 filler + 1 S-rank at pity 40, then 15 more filler on the next phase → current pity correctly reads 15, not 15+40 or reset-and-lost); a second S-rank pull reset the counter to 0 and updated the average; the Arc pool tracked completely independently of the Character pool throughout. Confirmed no 50/50 UI renders anywhere for N2E and that it does render correctly for Wuthering Waves (see above). `pnpm typecheck` and `pnpm build` clean. Test pull-log rows cleaned up from both games after verification.

## Stage 3 follow-up — income sources become real claims, not a blind toggle

You noticed that a non-Guaranteed income source never actually counted toward the currency totals, and asked for a way to make it count automatically without hand-editing the balance — tying into the not-yet-built Dailies checklist (checking off a task both completes it and credits the total). Two things came out of this:

- **A real bug, unrelated to the design question:** the Income Sources row editor never had a category `<select>` at all — every new row was hardcoded to "Guaranteed" on creation with no way to change it from the UI. That's why non-Guaranteed sources looked broken: there was no way to create one to test in the first place. Fixed — every row now has a category select, and moves section immediately when changed.
- **The actual design gap:** `enabled` was only ever a static "assume this keeps happening" toggle, blindly multiplied by cadence — never a record that something was actually claimed. Rebuilt around a real claim:
  - `income_sources.cadenceLabel` (free text) → `cadence` (fixed enum: `daily`/`weekly`/`bi-weekly`/`monthly`/`one-time`/`custom`) + `customCadenceLabel` (display text, only meaningful for `custom`). The fixed set is what lets cadence actually drive `intervalDays` instead of just labeling a number someone typed — `apps/web/src/features/planner/materialNeeds.ts`'s `CADENCE_INTERVAL_DAYS` derives it automatically for the five fixed cadences; `custom` is the only one where `intervalDays` stays manually set (for oddball real-world cadences like a patch-length event).
  - New `income_claims` table (`apps/api/src/db/schema.ts`) — one row per real "I actually got this" event, append-only. `POST /api/games/:game/income-sources/:id/claim` logs a claim and immediately credits `currency_inventory.balance` by `amountPerEvent` — real balance, not a projection.
  - `isClaimedThisPeriod`/`computeRemainingProjection` (`materialNeeds.ts`) — a recurring source is "claimed" if its most recent claim falls within the current `intervalDays` window; one-time sources are done forever once claimed at all. The Currency tab's "+X/window" figure changed from a blind `cadence × amount` multiply to **actual balance (already reflects every real claim) + remaining projection only for periods still ahead in the window** — a claimed period is never double-counted by also projecting it forward.
  - `IncomeSourcesTab.tsx` gained a CLAIM button per row (greys out to CLAIMED once covered for the current period) and the category select above. The Income Sources tab's own "/30d" column and MIX bar still use the old blind `computeIncomeProjection` deliberately — that's the honest *theoretical* ceiling ("if you keep this up"), distinct from the Currency tab's *actual* figure.
  - This is exactly the hook a future Dailies checklist (Stage 5) plugs into: it can auto-generate a task per enabled daily/weekly income source and wire its checkbox to this same claim endpoint, so ticking a daily task both completes it and credits the currency total. Not built yet — Dailies itself doesn't exist. One-off/speculative sources stay manual via the claim button, since there's no periodic task to auto-generate for them.

**Real bug found and fixed during verification, unrelated to the above design:** the Currency tab's balance input (and the Materials tabs' "have" stock inputs) used `defaultValue`, which only sets a DOM input's value once at mount — it never picks up a value that changes afterward from outside that same input (e.g. a claim made on a different tab crediting the balance behind the scenes). Confirmed via Playwright: a full page reload showed the post-claim balance correctly, but switching tabs within the same session (no reload) kept showing the stale pre-claim value indefinitely, even with a generous wait — not a timing race, a real staleness bug. Fixed by keying each of these inputs on their own current server value (`key={balance}` / `key={row.have}`), which forces React to remount the input (and thus reset `defaultValue`) whenever the underlying server value changes from any source, while leaving normal in-place typing/onBlur editing untouched.

**Verified:** `pnpm typecheck`/`pnpm build` clean; full migration/reseed cycle for both games. Via Playwright: added a source, confirmed the category select moves it between sections and updates the mix bar; set cadence to `daily` and confirmed `intervalDays`/theoretical projection auto-derive correctly (100/day → 3,000/30d); set cadence to `one-time`, claimed it, confirmed the button shows CLAIMED (disabled) and the theoretical projection drops to 0 (consistent with one-time never having been counted toward the recurring theoretical figure); confirmed the server-side claim really credits `currency_inventory` (checked directly via the API); confirmed the Currency tab reflects the real balance immediately after switching tabs, not just after a reload, once the `defaultValue`-staleness fix landed. All test income sources/claims/balances reset afterward.

## Stage 3 — Inventory, currency & resource planner (done)

Covers mockup screens 03 (Currency), 17 (Materials), 18 (Farm route), 19 (Income sources), plus the per-character Materials tab (screen 15) deliberately deferred from Stage 2. Full scope/design decisions are in `~/.claude/plans/starry-churning-balloon.md` from this stage's planning session; summarized here since the plan went through three real design pivots worth remembering before touching this area again.

**How "material need" ended up working, and why it changed twice:**
1. First pass: the mockup's "need" numbers assume a per-tier material-cost formula that doesn't exist in the data. Proposed a flat, manually-maintained "need" number per character+material (mirroring `character_stat_targets`) to avoid a big sourcing effort — agreed, with one flagged nuance (materials that convert/craft between tiers, including NTE's flexible "heterogeneous unit") resolved as a passive cross-reference rather than real conversion math (no ratio is tracked).
2. Second pass: a flat manual "need" goes stale the moment something is leveled up in-game — re-deriving what's still needed by hand (skill level N+1's cost isn't N's cost) is exactly the busywork the flat design was supposed to avoid. Reversed course: **real per-level material cost tracking**, sourced by the user directly, regardless of effort.
3. Third pass nailed the shape: per-level costs apply to **character level, weapon/Arc level, and skill level** — not module/Cartridge level (confirmed out of scope), not Bond (NTE-only, points-from-gifts rather than materials-per-level, a different data shape entirely — confirmed as a **separate future stage**, not built now). Character/weapon costs are **banded** (e.g. 1→20 costs one bundle, 20→40 another — an ascension-breakpoint shape, even though "ascension" itself isn't tracked as its own stat per Stage 2's earlier removal). Skill costs are genuinely **per individual level**. Weapon costs are **per individual weapon**, not shared across a rank tier (more sourcing work, the user's explicit call).

Net result: remaining need for character/weapon/skill level is **fully derived**, never manually tracked — `SUM(quantity) WHERE toLevel > currentLevel` over a sourced cost schedule, joined against the level that's already tracked. The instant a level is saved on the Build tab, every dependent Materials view recomputes with no manual re-entry. Verified live: bumped Zankou from level 15→25→35 with a 1→20/20→40 test schedule and watched the 1→20 band's materials (Crimson Filament, Ashen Beetle Shell) disappear from remaining need exactly at the 20 threshold, with no user action beyond saving the level.

**Shipped:**
- One shape reused three times (`apps/api/src/db/schema.ts`): `character_level_costs`, `equipment_level_costs`, `skill_level_costs` — each `{fromLevel, toLevel, materialId, quantity}`. Master data (real game facts, sourced once), not user-state, but no `masterDataColumns` either — same category as `module_targets`/`skill_materials`. Registered through the existing generic `childRows.ts` factory, which gained an optional `flatPath` (an unfiltered "every row for this game" GET alongside the parent-scoped one) since the global Materials planner has to aggregate across every character/weapon/skill at once — same dual-registration precedent as `skills` already having both a flat tab and a child-of-character view.

- User-state tables, unaffected by the above: `material_inventory`/`currency_inventory` (manual stock ledgers — no way around manual here), `income_sources` (cadence/amount are real facts, but `enabled`/`reliabilityPercent` are the player's own call, matching the original build-plan's user-state categorization), `farm_route_entries` — a **manual planning list only**: no farmable-stage catalog, no drop rates, no stamina cost, no auto-solve. The user's call: stamina isn't meaningfully tied to specific material stages (it's spent on plenty of other things too, so "stamina per material" is a pointless calculation) and farming plans are too personal to auto-solve. This also cut every mockup widget that depended on stamina/yield data that will never exist: RUNS/ETA columns, the 7-day farm grid, the stamina budget breakdown, the personal drop-rate log. Two more mockup widgets cut as flatly impossible regardless: "if you drop the pass" what-if (no real basis for scenario modeling) and the projection-accuracy tracker (needs a saved history of past projections vs. actuals that doesn't exist yet and can't retroactively exist).
- Routes: `inventory.ts` (upsert stock/balance), `incomeSources.ts` (flat CRUD, mirrors `teams.ts`), `farmRoute.ts` (flat CRUD + a `/reorder` action for drag-and-drop). `roster.ts` is untouched — the cost-schedule tables are catalog data fetched independently, not per-character state.

## Stage 1 follow-up — Cartridge vs. Module split

The previous follow-up added `module_targets` and treated "Modules" as one undifferentiated gear concept. The user (who plays the game) corrected this: NTE's Console system has two distinct pieces, and what was seeded as "modules" (Crimson: Twin Butterflies, Lost Radiance — set name + fixed dual main-stat + set bonus) was actually structurally a **Cartridge** (the main piece — a character equips exactly one, chosen from a fixed catalog, no multi-piece set bonus since only one is ever worn), not a Module. Confirmed the split with two direct questions rather than guessing from research alone:

- **Cartridge**: one equipped, no set-bonus mechanic. `setName`/`setBonusText`/`setPieceCount`/`slot` don't apply to these rows.
- **Module**: the sub-pieces. Each is a fixed *shape* (`slot`: capped select `2`/`3`/`4` — confirmed as a small fixed set, not free text) with RNG substats locked in on acquisition (never rerolled). Modules form sets: equipping `setPieceCount` copies of the *same shape* unlocks `setBonusText`; extra copies beyond that are still equippable for raw stats without adding to the bonus (that distinction is Stage 2 build logic — this table only records the catalog fact "this shape's bonus needs N").

Kept both in the same `modules` table/tab (per the user — "fine to include them in the same tab as modules... categorize based on type"), split by a new `pieceType` field (select, game-config-driven via `pieceTypes` in `config.ts`, currently `["Cartridge", "Module"]`).

The other key correction: a single module/cartridge shape is normally farmed **multiple times** for different characters with different substat priorities — not an edge case to special-case, the normal case. `module_targets` gained `forCharacterId` (nullable — a target can still be character-agnostic) so the same piece can have several target rows, one per character that needs a copy. Seed data now demonstrates this directly: two separate target rows for `crimson-twin-butterflies`, one for Zankou and one for Daffodill, each with its own substat priorities.

Cleared the previously-fabricated `mainStat`/`setBonusText` values on the two reclassified Cartridge rows rather than leave now-known-wrong data in place — Cartridges' real main-stat mechanics (does it vary per instance? per a fixed slot-position pool?) are still unconfirmed, so those fields are just empty pending real data rather than guessed at again. `gameBundle.ts`'s export/import extended to carry `forCharacterSlug` on module targets the same way as its other slug references. Migration regenerated from scratch again (still no real user data at stake).

## Stage 1 follow-up — schema/UX revision from design feedback

The user reviewed the shipped master-data model and gave a batch of logic-level feedback. All addressed:

- **Materials `dropsFrom` → `material_sources` child table.** A single text field was misleading for materials with multiple real sources (and risky if something downstream ever keys off it for farm-route tracking). Now a material has zero or more named source rows, edited inline from its record editor. `category` was left as free text after discussion — it's purely descriptive and nothing in the code gates on it, so a material can already be both a character's ascension material and a skill's material at once regardless of its category label.
- **Materials `tier` capped 1–6.** Was an unbounded number field; gacha material tiers don't realistically exceed ~6, so it's now a `select` with fixed options (schema column is still a plain integer — only the UI is capped, so raising the ceiling later is a one-line change, not a migration).
- **Skills drastically simplified.** Dropped `maxLevel`/`scalesWith`/`effectText` — the tracker assumes a build target is always max level, so none of that is needed. The single `materialId` FK became a `skill_materials` join table (a skill can need more than one material). Only name/owner/slot/materials remain.
- **Modules: "ideal target piece" tracking added.** New `module_targets` child table — a module (set+slot) can have multiple named target specs (e.g. "Crit build" vs "ATK build", confirmed with the user rather than assumed), each with a main-stat target and a substats list stored as `{stat, value}` pairs (structured tags, not full child rows — no priority ranking, per the user's "somewhere in between" call). Explicitly scoped as master data only: comparing an owned piece against a target and marking it "achieved" is user-state/inventory, a Stage 2 concern to build on top of this later, not something added now.
- **Elements and Banners now support images** (`hasImage: true`) — no schema change needed, just enabling the existing path-convention image system for these two entities.
- **Event rewards → `event_rewards` child table.** A single `currencyReward`/`materialRewards` pair couldn't represent an event with several rewards of different kinds. Now a list of `{kind: currency|material, ...}` rows, editable inline (currency dropdown sourced from the game config, material via relation).
- **Save button bug fixed.** Reported as "no visible effect" — root cause: the update path never closed the drawer *or* showed any confirmation (only create did). Fixed with a transient "Saved ✓" flash instead of auto-closing on update (auto-closing was actually wrong once child sections exist — you want the drawer to stay open so you can immediately add sources/materials/targets/rewards to what you just created). Create now transitions the same drawer into edit mode for the new row instead of closing, for the same reason.
- **Full-game export/import extended** to cover all 4 new child tables too (in `apps/api/src/core/gameBundle.ts`), matched on a natural key per table (e.g. a material source on `materialSlug`+`name`) so re-importing updates in place rather than duplicating — same idempotent behavior as the 8 main entities.
- Migration was regenerated from scratch (dev data only, all reseeded) rather than hand-writing an ALTER-heavy incremental one, given nothing real depends on the old shape yet.

**Unplanned but welcome discovery during verification:** the user has already been dropping real NTE image assets into `data/images/<game>/<entity>/` outside of the app's upload UI — confirmed the case-insensitive slug-matching path convention picks these up correctly with zero code changes needed. There are more character/material/module images present than currently-seeded rows (e.g. Chaos, Zero, Hathor, and others have images but no character row yet) — nothing broken by this, just noting it so a future seed-data expansion pass doesn't miss that the images are already sitting there.
